# ADR 0001. Архитектура фронтенда (клиента)

- Статус: принято
- Дата: 2026-10-01
- Контекст сессии: решение принято после проверки возможностей Telegram Mini Apps
  (`shareToStory`) и обсуждения вариантов стека и структуры репозитория.

## Контекст

Бэкенд (`stories-backend`) завершён и развёрнут: по URL видео он скачивает
исходник, перекодирует под Telegram (вертикаль, форсированные кейфреймы),
нарезает на куски mp4 и отдаёт манифест и куски. Публикация в Telegram Stories
выполняется **вручную** пользователем из мобильного Telegram - программного API
постинга историй от имени пользователя нет (зафиксировано в `CONTEXT.md`).

Отсюда задача клиента узкая: ввести URL -> создать задачу -> показать прогресс
-> отдать готовые куски так, чтобы их было удобно опубликовать в Stories. Любой
выбор технологии оценивается по одному критерию: насколько гладко закрывается
последний шаг «кусок -> редактор историй Telegram».

Входные данные:

- API бэкенда: REST + SSE, аутентификация по `X-API-Key` (изоляция по `key_id`),
  развёрнут по подпути `/instore` за nginx (`https://360tur.uz/instore`). Есть
  OpenAPI-контракт. Куски - mp4, TTL 1200 c, вертикаль обеспечивается режимом
  `stories_fit` (`cover`/`pad` -> 1080x1920). Лимит исходника `MAX_FILESIZE_MB=50`.
- Навыки разработчика: TypeScript (недавно), Python; приоритет строгой типизации
  и методологии.

## Проверка ключевой возможности: Telegram `shareToStory`

(Пункт исследования, на котором основано решение.)

- Метод `shareToStory` (событие `web_app_share_to_story`) добавлен в Bot API 7.8
  (июль 2024) - зрелая возможность.
- Поддерживает **вертикальное видео** (mp4), открывает родной редактор историй.
- Параметры: `media_url` (обязательный), `text` (подпись), `widget_link`
  (только Premium, не используем).
- Ограничения, критичные для нас:
  1. `media_url` должен быть **публично доступен по HTTPS** - Telegram сам тянет
     файл и **не передаёт `X-API-Key`**. Текущая отдача кусков закрыта ключом,
     то есть для шеринга нужен отдельный публичный доступ к куску.
  2. История - вертикальное видео, **максимум 30 МБ**.

## Рассмотренные варианты (технология)

- **Flutter (нативное приложение).** Отклонён: публиковать Stories всё равно
  нельзя программно (как и в любом варианте), выгода - лишь UI и сохранение в
  галерею; цена - новый язык (Dart), сборки, подпись, дистрибуция через стор.
  Избыточно для личного инструмента на одного пользователя.
- **Telegram Mini App (TypeScript).** Выбран. `shareToStory` закрывает последний
  шаг максимально близко к «публикации в один тап»; работает внутри уже открытого
  Telegram; стек TS совпадает с навыками; деплой - статика за тем же nginx.
- **Адаптивный веб-PWA (TypeScript).** Запасной вариант на случай, если
  `shareToStory` окажется неприменим: тот же стек и деплой, но последний шаг -
  «скачать на устройство, дальше вручную».

## Решение

1. **Технология: Telegram Mini App на TypeScript.** Публикация каждого куска -
   через `shareToStory` (вертикальное mp4, `stories_fit` = `cover`/`pad`, размер
   ≤ 30 МБ). Запасной путь (PWA со скачиванием) держим как деградацию, не как
   основную ветку.
2. **Структура репозитория: монорепо.** Клиент - каталог `frontend/` в
   `imchrm/instore`. Причины: один разработчик; клиент жёстко завязан на API
   именно этого бэкенда (контракт и клиент удобно менять атомарно); общая
   документация. TS-тулчейн сосуществует с Python (отдельные каталоги, отдельная
   CI-джоба; существующий `ci.yml` проверяет только `src/`). Выделение в отдельный
   репозиторий оправдано лишь при независимом релизном цикле или open-source
   клиента - сейчас это лишний оверхед.
3. **Публичная отдача кусков для Telegram: подписанный URL (HMAC + TTL).**
   Добавляется публичный маршрут отдачи куска, доступный без `X-API-Key` только
   при валидном коротко живущем токене в query (подпись HMAC-SHA256 над
   `job_id` + индекс + срок действия, секрет - из ENV). Mini App запрашивает
   такой URL у API (под `X-API-Key`) и передаёт его в `shareToStory`.
4. **Авторизация клиента в API: `X-API-Key`** (как сейчас). На клиенте ключ
   хранится в конфигурации; для личного использования допустимо. Переход на
   авторизацию Mini App через Telegram `initData` (валидация на бэкенде) -
   возможное усиление в будущем, вне объёма первой версии.

## Последствия

Положительные:

- Лучший для сценария UX: куски попадают прямо в родной редактор историй.
- Единый стек TS + генерация типизированного клиента из OpenAPI -> сквозная
  типобезопасность.
- Простой деплой: статика за nginx рядом с API, без сторов.

Издержки и необходимые доработки бэкенда (новая итерация, проект уже не «только
бэкенд»):

- **Эндпоинт подписанных URL для кусков** (HMAC + TTL, секрет из ENV). Это
  основное добавление; без него `shareToStory` не сможет забрать файл.
- **Гарантия размера куска ≤ 30 МБ** для Stories (проверка/флаг и/или рекомендация
  по `max_height`; возможно, отдельный дефолт высоты для вертикали).
- Генерация TS-клиента из OpenAPI и CI-джоба для `frontend/`.
- Привязка к платформе Telegram (при основном пути). Запасной PWA снимает её
  ценой UX.

## Открытые вопросы

- Стратегия «≤ 30 МБ»: понижать дефолтный `max_height` для Stories, добавить
  size-guard, либо и то и другое.
- Хранение `X-API-Key` на клиенте против авторизации по `initData`.
- Выбор фреймворка клиента (решается на этапе скелета): кандидаты - минимальный
  Vite + TS, либо Svelte/React при росте UI.

## План реализации (следующие шаги)

1. Backend: эндпоинт подписанного URL для кусков (HMAC + TTL) и size-guard под
   лимит Stories 30 МБ.
2. Frontend: скелет `frontend/` (Vite + TS, Telegram WebApp SDK, клиент из
   OpenAPI), CI-джоба.
3. Сценарий публикации: создать задачу -> прогресс (SSE) -> по готовности для
   каждого куска запросить подписанный URL -> `shareToStory`.
