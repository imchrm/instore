# CONTEXT — stories-backend

Контекст проекта: назначение, границы, зафиксированные решения и ограничения серверной части.
Документ описывает «зачем» и «что». Технические детали «как» — в `ARCHITECTURE.md`.

- Проект: tg-stories-app
- Модуль: `stories-backend` (Python 3.12+ / FastAPI)
- Статус документа: согласован (базовый набор решений зафиксирован)
- Язык рабочей документации: русский; идентификаторы кода — английский
- Кодировка файлов: UTF-8

## 1. Назначение

Приватный бэкенд-сервис, который по URL видео с YouTube/Instagram:

1. скачивает исходник (`yt-dlp`);
2. перекодирует его в совместимый с Telegram формат (`ffmpeg`) с гарантированными кейфреймами на границах сегмента;
3. нарезает на куски длительностью не более 45 секунд без перекодирования;
4. измеряет фактические параметры кусков (`ffprobe`) и формирует манифест;
5. отдаёт мобильному клиенту манифест и сами файлы кусков.

Публикацию кусков в Telegram Stories выполняет пользователь вручную из мобильного клиента через системный share. Сервер в публикации не участвует.

## 2. Пользователи и режим эксплуатации

- Сервис не публичный, без регистрации и без мультиарендной модели с ролями.
- Владелец один, но допускается несколько пользователей и несколько устройств. Разграничение — по API-ключам (см. раздел 5).
- Ожидаемая нагрузка низкая: одна активная обработка за раз (`MAX_CONCURRENT_JOBS = 1`).

## 3. Область (scope)

В области:

- Приём задачи по URL и асинхронная обработка (download → transcode → segment → probe → ready).
- Трансляция прогресса обработки в реальном времени (SSE).
- Выдача манифеста задачи и файлов кусков.
- Опциональное приведение кадра к вертикали 1080x1920 под Stories.
- Управление жизненным циклом задач и автоматическая очистка по TTL.
- Разграничение доступа и cookies по API-ключам.

## 4. Вне области (non-goals)

- Автоматическая публикация в Telegram Stories (userbot/MTProto). Не реализуется и не закладывается в архитектуру (нет соответствующего порта).
- Хранение истории/галереи скачанного, аккаунты, роли, биллинг.
- Веб-интерфейс. Наружу — только REST/SSE API для мобильного клиента.
- Горизонтальное масштабирование (несколько воркеров/машин).

## 5. Зафиксированные решения

Очередь и хранение задач:

- Обработка — in-process asyncio-воркер (без внешнего брокера).
- Персистентность задач между рестартами — SQLite.
- `arq` + Redis сознательно не используем: дают лишние постоянные процессы и накладные расходы без пользы при одном владельце и одной параллельной задаче.

Ограничения источника:

- Максимальный размер исходного видео — `MAX_FILESIZE_MB = 50`. Значение осознанное (при 1080p это примерно 2–4 минуты видео); меняется одной строкой конфига.
- Проверка размера в два этапа: по метаданным `yt-dlp` до скачивания и жёстко через `--max-filesize` во время скачивания. Превышение → `failed` с кодом `TOO_LARGE`; клиент предлагает ввести другое видео.
- Максимальная высота по умолчанию — `MAX_HEIGHT_DEFAULT = 1080`; клиент может запросить меньше.

Жизненный цикл файлов:

- `JOB_TTL_SECONDS = 1200` (20 минут) — время жизни готовых кусков после готовности задачи.
- Промежуточные файлы (`source.*`, `conv.mp4`) удаляются сразу после успешной нарезки и `probe`.
- По истечении TTL куски удаляются, задача переходит в статус `expired`.

Нарезка:

- `SEGMENT_TIME` по умолчанию 45 секунд.
- Жёсткий предел куска `KEYFRAME_LIMIT_SEC = 60`; кусок с большей длительностью помечается флагом `over_limit` в манифесте.
- Точность границ обеспечивается принудительными кейфреймами на шаге transcode, поэтому нарезка выполняется копированием (`-c copy`).

Приведение под Stories:

- Параметр `stories_fit: none | cover | pad`, по умолчанию `none`.
- `none` — кадр не меняется; `cover` — масштаб и обрезка по центру до 1080x1920; `pad` — вписывание с размытым фоном до 1080x1920.
- Выполняется на шаге transcode (там уже идёт перекодирование).

Доступ и cookies:

- Аутентификация по статическому API-ключу в заголовке `X-API-Key`. Ключей может быть несколько (по устройству/пользователю), формат конфига — пары `имя:ключ`; из имени формируется стабильный `key_id`.
- Изоляция задач по `key_id`: задача доступна только тому ключу, которым создана.
- Instagram cookies хранятся отдельно по `key_id` (`COOKIES_DIR/{key_id}.txt`). Общий fallback-файл не используется.
- Загрузка/проверка/удаление cookies — отдельные админ-эндпоинты, вне основного потока создания задачи.
- Использование cookies при скачивании включается флагом `use_cookies` в запросе задачи; при `use_cookies=true` и отсутствии файла — отказ `AUTH_REQUIRED`.

Выдача файлов и прогресс:

- Файлы кусков в продакшене отдаются через `X-Accel-Redirect` (nginx); в dev — через `FileResponse`.
- Прогресс обработки транслируется по SSE.
- Лимиты и дефолты сервер публикует через `GET /api/v1/config`, чтобы клиент показывал их до отправки задачи.

## 6. Ограничения и риски

- `yt-dlp` регулярно ломается при изменениях YouTube/Instagram; требуется механизм обновления бинарника (см. деплой в `ARCHITECTURE.md`).
- Instagram практически всегда требует актуальные cookies; они периодически протухают (признак — ошибки `AUTH_REQUIRED`).
- Скачивание контента с YouTube/Instagram противоречит их ToS; сервис приватный, для личного использования, вопрос ответственности на владельце.
- Сборка `ffmpeg` с `libx264` подпадает под GPL; для приватного использования ограничений нет, фиксируется как примечание при сборке образа.

## 7. Глоссарий

- Задача (job) — единица обработки одного URL от приёма до готовности или ошибки.
- Кусок (chunk) — один нарезанный сегмент готового видео.
- Манифест — описание готовой задачи: перечень кусков с их параметрами.
- TTL — время жизни готовых кусков на сервере до автоматического удаления.
- key_id — стабильный идентификатор API-ключа, к которому привязаны задачи и cookies.
- stories_fit — режим приведения кадра к вертикали 1080x1920.
